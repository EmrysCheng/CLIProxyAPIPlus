# 两个基础项目直接自更新（0.4.0）

当前版本为 `0.4.0`。本次 Release 提供源码，若需要下面的完整 Portable 布局，请先按仓库开发指南构建；下文不表示已有可直接下载的安装包。

## 1. 本轮需求与实现方式

本方案按 2026-11-04 的需求调整，替代“必须启动额外发行服务、准备发行索引”的默认更新方式。管理页面直接检查以下固定仓库的最新正式版：

- `router-for-me/CLIProxyAPI`
- `seakee/CPA-Manager-Plus`

可以单独更新任一基础项目，或一起更新。选择单个项目时，另一个项目保持当前精确提交。**不直接安装两个原版 EXE/HTML**：它们已在源码层面嵌入一个程序，必须在隔离目录重新构建整合程序，再使用原维护引擎备份、切换、验证健康和成对回滚。

不需要 `--release-index`、不需要 `index.json`、不需要启动 26973 或其他发行 HTTP 服务。常驻的仍是一个业务进程、一个业务监听端口。更新过程中会启动受控的临时源码下载/编译/测试/安装辅助进程，验证用例也可能临时使用回环端口；不是新增常驻业务服务。

这是使用安装包内置构建工具的源码自更新：无需用户下载 Python / Go / Node / npm 或配置 PATH；不是“无工具运行原版自动更新”。不承诺任意未来上游提交都能免适配：补丁、模块边界、测试或构建不兼容时明确失败，旧程序和业务数据不动。

## 2. 第一次换成支持此功能的程序

0.3.x 不包含新的源码自更新入口。先正常退出旧应用、做好外部备份，然后将完整的 **0.4.0 Portable 包**解压到新安装目录，保留并使用原配置和 data 路径。包内有：

```text
cliproxyapi-plus.exe                    # Linux 无 .exe
updater-source/                        # 与该程序身份匹配的源码配方，不要删
  source-kit.json
  upstream.lock.json
  cmd/ internal/ patches/ scripts/ ...
  upstream/cliproxyapi/                 # 原始只读源码快照
  upstream/cpa-manager-plus/
build-tools/                           # 与目标平台匹配的 Python/Go/Node/npm，不能删
  toolchain-manifest.json               # 版本、逐文件 SHA256、可执行权限清单
  python/ go/ node/ python-licenses/
update-tools.json                      # 已配置相对路径 ./build-tools，不需手工修改
update-tools.example.json               # 仅用于高级自定义工具路径
...
```

**不要仅复制 EXE 后丢掉 updater-source/build-tools/update-tools.json，也不要对已有实例执行 --init。** 自定义源码目录必须与当前可执行程序的源码 SHA256、上游 lock 摘要和两项目提交相符，不是填任意项目源码路径。

## 3. 构建工具已内置，无需下载或配置 PATH

完整 Portable 安装包按目标平台内置：**Python 3.13.18、Go 1.26.10、Node.js 24.22.1、npm 11.19.1**。Go/Node 来自官方归档，便携 Python 来自 Astral python-build-standalone `20261026`；原始许可及构建仓库的依赖许可文本均随包保留。归档内安全链接会物化为普通文件；Linux Python 仅排除与构建无关、含大小写重名的 share/terminfo 终端数据库，其余运行时/标准库保留。Linux 工具要求 glibc 2.28+；不适用于 Alpine/musl。平台打包不等同于该平台已通过原生验收。

默认 `update-tools.json` 已包含以下内容，**不要再复制空的 example 文件覆盖它**：

```json
{
  "bundle": "./build-tools",
  "go_proxy": "https://goproxy.cn|https://proxy.golang.org"
}
```

路径相对此 JSON 文件所在目录解析，可以将整个目录解压到含空格的新路径；程序不修改系统 PATH、注册表或全局 Go 配置，不使用系统旧 Go/Node。工具清单 SHA256 固定在产品二进制中，执行前核对平台、文件、权限及版本；缺失/被修改时阻止构建，不偷偷改用 PATH。页面显示“安装包内置”和工具版本，不暴露本机路径。

**工具内置不等于离线更新。** 获取 GitHub 元数据、上游源码 ZIP、Go modules 与 npm 锁文件依赖仍需网络。GitHub 网络错误/限流独立于工具状态；工具就绪并不保证 GitHub 能访问。不需 Git 客户端。内置 Go 子进程设置 `GOTOOLCHAIN=local`、`GOENV=off`，禁止暗中下载另一版本 Go SDK；未来上游若要求新 SDK，构建会明确失败并保留旧服务，需安装已验证的新整合发行包或由高级操作者配置受信任的新 SDK。

源码更新构建下一份发行包时复用并再次校验已内置的 SDK，**不再次下载 SDK**；安装/回滚仍只切换已验证的整合程序、配置/data 和源配方引用，原安装目录的 SDK 保留供后续更新使用。升级成品仍是单业务程序，不常驻运行工具或额外发行服务。

### 构建网络：Go/npm 依赖仍须可访问

2026-11-04 的一次实际失败（操作 4c06041a…）发生在 Go 依赖获取：连接默认 `proxy.golang.org` 超时，尚未安装。这不是 SDK 缺失，也不能通过关闭测试或校验来修复。

**普通 `go env -w GOPROXY=...` 对包内 SDK 构建不生效**：包内工具有意使用 `GOENV=off`，避免加载宿主旧 SDK 的全局配置。当前版本按用户明确选择，在安装包中预置 `https://goproxy.cn|https://proxy.golang.org`；不接受网页提交命令或代理配置。可按自己的网络策略调整：

1. 直接使用随包默认值，无需运行 `go env -w`。要更换代理，修改实际使用的 `update-tools.json` 中的 `go_proxy`；字段非空时优先于启动环境中的 `GOPROXY`。
2. 要继承启动环境中的 `GOPROXY`，先删除 `go_proxy` 或将它设为 `""`，保留 `bundle`；然后在启动应用的终端设置环境并启动/重启。已经运行的进程不会自动获得后来设置的环境变量。`HTTPS_PROXY` 等网络代理环境仍由操作者配置。

默认配置示例（`npm_registry` 默认不写入安装包；需要时可另行添加可信 HTTPS 地址）：

```json
{
  "bundle": "./build-tools",
  "go_proxy": "https://goproxy.cn|https://proxy.golang.org"
}
```

只需要覆盖的字段才填写；未填写时保留启动环境/工具默认值。`go_proxy` 对应 Go 的 `GOPROXY`，`npm_registry` 对应 npm 的 registry；不会修改系统全局配置。Go 模块代理列表中的 **`|` 在网络错误等任意错误时尝试下一项，`,` 仅在 404/410 等规定响应时回退**；仅把直连放在默认代理逗号后面，不能解决连接超时。`direct` 模式可能需要 Git 等 VCS 客户端，不是无外部 VCS 工具部署的默认建议。

代理/registry 地址只接受 HTTPS、不得内嵌凭据或查询参数，不从页面暴露这些本机设置；需要带凭据的网络代理时由操作者安全配置启动环境，避免将秘密放入命令历史或截图。本包按用户要求预选 goproxy.cn 并以 proxy.golang.org 作为回退，属于可修改的本机配置，不会在失败后擅自切换到列表外的镜像；不设置 `GOSUMDB=off`、不关闭 TLS 或 npm 锁文件完整性校验。私有模块还需操作者按自己的组织策略配置，不能承诺任意网络均可访问。配置后由管理员重新检查并手动确认重试，不自动重放失败升级。

### 开发者打包

`python scripts/project.py build --target windows/amd64`（另支持 `linux/amd64`、`linux/arm64`）在**打包机器**下载锁定的工具归档、校验 SHA256 并内置到成品；缓存位于 `.build/toolchain-downloads`。`--tool-bundle <已有验证的 build-tools>` 可复用完全匹配的工具包而不下载 SDK。普通构建绝不更新锁定值；维护者有意更新 SDK 时需重新核验来源、许可并使用 `scripts/toolchains.py seal --target ...` 重新生成三个平台清单锁，完成全套验收。新 SDK 自身的兼容性不能由校验和替代。

## 4. 启动命令

在实际部署目录，保留原 config/data 路径：

```powershell
.\cliproxyapi-plus.exe --config config.yaml --data-dir data --web-updates --source-updates
```

默认读取 EXE 旁的 `updater-source` 与 `update-tools.json`。如果工具配置另有位置：

```powershell
.\cliproxyapi-plus.exe --config config.yaml --data-dir data `
  --web-updates --source-updates `
  --source-tools "D:\Deploy\CLIProxyAPIPlus\update-tools.json"
```

可选 `--source-workspace <绝对路径>` 仅指定与当前程序匹配的源配方；后续源码升级会自动保存并切换到本次已验证的候选配方，回滚时恢复旧配方引用。

移除旧命令中的 `--release-index`、`--allow-local-release-http`、`--release-ca-file` 即可不使用发行源；也要清理仍设置着的 `CLIPROXY_PLUS_RELEASE_INDEX` 环境变量，避免它被当成可选发行索引读取。旧发行源方式仅保留为高级兼容选项，不是此功能的依赖。

`--web-updates` 允许安装/回滚；`--source-updates` 是额外的**执行受信任上游构建代码**授权。两者均显式开启后才允许源码安装，未开启也可以看版本检查提醒。

继续受独立 Portable、固定监听 IP/端口、自包含 auth/TLS、私有可写目录等限制；不要与 Windows Service/systemd/容器自动拉起混用，不要手工绕过页面禁用原因。

1. 使用 Manager **管理员凭据**登录，打开更新页。普通 API key、core management key 不能执行管理操作。

3. 点击“更新 CLIProxyAPI”“更新 CPA-Manager-Plus”或“一起更新两个项目”。输入页面展示的版本确认文本，并明确勾选信任目标源码执行的确认。浏览器只提交项目 ID 和已检查提交，不提交命令、文件路径或 URL。
4. 后端重新检查固定仓库并锁定提交；不同于刚确认的版本/提交会拒绝，需刷新。构建时不再跟随移动标签。只更新一个项目时另一项目固定在当前运行提交。
5. 旧服务继续工作；后台私有目录复制配方、下载源码、严格应用适配补丁、重新构建前端/后端，执行产品测试、单端口测试、维护升级/回滚测试、前端测试、适配回归及二进制/离线维护烟测。任何必要验证失败都不安装，不“忽略失败继续更新”。
6. 验证通过才校验目标整合包、程序源码身份、两个上游精确提交和更新协议，正常排空旧程序、备份程序/配置/数据库/密钥/认证，再替换并检查新进程健康。页面短暂断线后重连，不要重复提交或启动第二实例。
7. 成功记录中可以“恢复升级前的双上游组合”。回滚仍需旧整合版本确认和数据快照恢复确认，恢复程序/双上游组合/配置/data/原源码配方引用。

基础项目更新时，**整合程序版本号可能不变**，应以两个项目的版本和提交号及维护记录为准，不要据整合版本号相同断言没更新。

回滚不是任选旧项目标签重新编译，不是单独降一个二进制：必须使用与当前程序匹配的成功记录和快照。恢复后不会合并快照之后的用量/业务修改；当前数据另行保留供人工检查。安装/迁移失败自动尝试成对恢复；无法确认安全恢复则保留维护标记，停在 recovery_required，按 OPERATIONS_CN.md 离线恢复。

## 6. 信任、资源与故障

- 构建/测试执行的是经管理员确认的固定 GitHub 仓库代码，权限与服务账户相同。隔离目录、提交固定、摘要校验和尽力清理敏感环境变量**不是 OS 安全沙箱**，不能用于不可信仓库；源码可能访问该账户可访问的网络/文件。使用专用最小权限账户并保存独立外部备份。
- 源配方的产品记录摘要必须等于运行程序内嵌摘要，lock 摘要绑定运行程序，完整文件摘要和两份快照树摘要均核对后才执行工具；不从活动 `upstream/` 原地修改或自动 promote。
- 构建进程受到超时和进程树/作业生命周期控制，正常关闭应用时取消构建。服务故障/断电产生的不完整候选不等同于已安装成功；必要时离线核查私有记录。
- 需要额外磁盘空间和 CPU/内存；首次依赖下载/编译可能较慢。每次构建日志在 `<data-dir>.updates/<operation-id>/source-build.log`，最多记录 64 MiB；预检阶段失败另见同目录 worker.log；网页仅显示阶段/受控错误。
- 该私有操作目录也可能包含**当前正在使用的下一次源码配方**和回滚快照，不要删除。工具安装和操作者的工具路径文件不由程序降级/卸载；应自己保留并管理。
- GitHub 匿名 API 有限流；操作者可在启动环境配置最小权限 GH_TOKEN/GITHUB_TOKEN 用于固定 API 元数据查询，不在网页接收 Token，构建子进程会移除常见 Token 环境变量。GitHub 不通/限流、工具不足、配方不匹配、补丁漂移、候选编译或验证失败均在页面明确显示，旧服务不停止。不能把检查失败显示成“已经最新”。
- 新正式版低于当前版本或不是可比较的受支持版本时禁止自动降级。当前请求只跟踪正式版，不无审批追随 main。

### v8.0.55 KV 数据库与回滚边界

新上游增加本地持久化 KVStore，默认数据库在 `<auth-dir>/kv.db`。开启
`--web-updates` 时，程序启动前和所有配置解析/保存/热重载都会检查有效数据库
路径必须位于 data-dir 内，并拒绝已有符号链接/junction 祖先。显式相对路径
按运行进程的工作目录解析，与上游打开文件的语义一致；启动时 auth-dir 先按原有规则相对配置目录规范化；
策略不对配置副本伪造规范化，而是验证上游返回的实际有效路径。若配置目录
与工作目录不同，建议使用绝对 auth-dir/KV 路径，避免重载指向其他位置。禁用 KVStore 时也不允许预设外置路径，以避免后续启用
时绕过快照边界。检查不创建、搬迁或重写数据库。

需要自管外置 KVStore 的部署不要开启网页升级，须离线备份/恢复其全部状态。
标准默认路径仍由原 data 快照成对覆盖；本次不扩展快照格式。该限制在候选
首次启动（打开 KV 文件之前）也执行，因此旧版中尚未识别的外置配置不会在
切换到新上游后先创建外部数据库再回退。路径检查不构成对恶意同账户并发
替换路径的 OS 安全沙箱。


网页升级模式还会拒绝以 `~` 开头的 KV 路径（包括 `~/`、`~\` 等），请显式
填写 data-dir 内的绝对路径；避免把上游主目录展开误当成数据目录中的普通
相对路径。Windows junction 在当前 Go 中可能标记为 ModeIrregular，已和
符号链接一并拒绝，并要求已有祖先为目录、叶节点若存在则为普通文件。
真实 Windows junction 与主目录路径的回归会随源码构建执行，不以普通
symlink 测试因创建权限不足而跳过替代 junction 检查。


### Windows NTFS 命名流限制（补充审查）

按 2026-11-05 用户确认，网页升级模式禁止将 KV 数据库配置成 NTFS 命名流，
例如 `data/carrier:kv.db`、`carrier:kv.db:$DATA` 或 `carrier::$DATA`。
这类内容不会被当前普通文件枚举/字节复制快照完整收集；不通过扩展快照格式
或搬迁数据库绕开限制，而是在启动、解析、保存、重载共用策略中提前拒绝。

只拒绝 Windows 卷名前缀以外的冒号，在相对路径解析前和绝对路径解析后均
检查。正常 `C:\...\kv.db` 的盘符冒号不受影响；普通相对/绝对路径仍须位于
已覆盖的 data-dir 内。不会打开、创建、截断命名流或其载体文件；禁用 KVStore
也不允许预设这种路径。未启用网页升级的离线自管行为及快照协议保持原样。


### 上游心跳回归的时序适配

实际完整验收发现上游 `TestServiceHeartbeatFailoverDoesNotDrainBlockingScope`
的 1 秒等待会与合法心跳检测加初次 0.5～1 秒随机退避重叠，独立 20 次运行
出现 18 次通过、2 次失败。配方对该固定哈希的测试夹具做显式适配：采用同类
用例已有的 `3 * homeSubscriberRetryInitial` 等待界限，同时在等待全程、
收到订阅及 ACK 后持续核查不得排空活跃请求，保留所有原有身份、ACK、取消
与注册表断言。没有改生产重连逻辑、没有跳过测试，也不靠自动重试掩盖失败。

新增离线配方回归、独立重复运行及延迟注入错误排空的反向验证；最终整套
验收仍须绑定最新源码摘要，先前失败保留，不作为成功依据。


## 9. 随包 Go 代理默认值

此前包生成器只写入 `bundle`，导致新包没有用户指定的 Go 模块代理。当前打包器将
`go_proxy: https://goproxy.cn|https://proxy.golang.org` 写入三个平台的实际
`update-tools.json`，后续页面源码升级产生的完整安装包也使用同一生成逻辑。
高级自定义路径示例 `update-tools.example.json` 不变，不应覆盖实际配置。

旧安装也可只在实际使用的 `update-tools.json` 中补上此字段并保留其他已有项；
保存后，在页面重新检查工具状态并手动发起新的构建，配置会在工具检查/构建时
重新读取，不会自动重试之前失败的升级，也不需要启动发行服务。


## 10. 公开源码仓库的固定快照补齐

公开 Git 仓库只保存整合产品、补丁和锁定清单，不再次提交原始上游快照中的 OAuth 应用常量。首次克隆后先执行 `python scripts/hydrate_upstreams.py`，再执行原构建命令；CI 和 Docker 采用同一路径。下载仅接受两个指定官方仓库的完整提交，核对固定树摘要、模块身份和 LICENSE，不查询移动 tag，不修改锁定值，不覆盖已有快照。`--offline` 可验证随源码交接的既有快照，缺失时明确失败。

这不是绕过 GitHub 密钥保护的豁免，也不是 OAuth 常量已完成安全审核的结论；原始第三方源码只从其原发布位置获取，不将常量移入其他产品文件或编码隐藏。本次正式源码发行不包含原始快照或安装包附件。任何二进制/完整源配方的公开再分发仍须经过第三方源码、安全、许可及对应平台验收，不能仅凭正式版本号或 Git 推送成功省略审查。原本安装目录、用户密钥和数据没有因此改变。


公开 CI 仅按白名单导出构建身份、校验和及候选验证元数据，不自动上传二进制、完整源码、安装归档或宽泛日志/报告目录；整包再分发仍须单独完成安全与正式发布审批。
